# architecture
Adapt to scale and existing conventions. Simple projects need simple layouts; complex domains may use domain/application/infrastructure; larger systems may group by business module. Do not impose Clean Architecture on every project. Dependencies point inward when layered. No empty folders, speculative extensions or unnecessary layers. Group related use cases in cohesive classes, neither one class per operation nor a god object. Prefer composition. Public APIs should hide internal complexity. Ask before changing architecture, contracts, schemas or dependencies. Preserve host ownership of resources in libraries.
